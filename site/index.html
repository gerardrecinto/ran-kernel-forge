How it works

Treat kernel readiness as a preflight checklist, not a post-incident discovery.

1

Profile per node type

Config fragments for DU, CU and RU merge into any existing kernel config with one script. DU and RU target a real-time kernel.

2

Tune the host

Scripts set hugepages, IRQ affinity and CPU isolation so the RAN stack gets cores the scheduler leaves alone.

3

Check before scheduling

A validator container fails fast in CI or on the node. Quick mode checks config only. Full mode adds a cyclictest latency gate.

Run it

Linux on x86_64 or arm64. Full mode needs rt-tests and root.

python3 tests/latency_check.py --quick
python3 tests/latency_check.py --max-latency-us 50
python3 tests/latency_check.py --quick --json
scripts/apply-profile.sh profiles/du-profile.config <kernel-src>
scripts/tune-hugepages.sh
scripts/tune-cpu-isolation.sh

The README also lists validation container images for DU, CU and RU.

What this does not do
  • It does not build or boot a kernel. The profiles are config fragments, reference quality, validated by the author on the kernel versions named in each file.
  • The checks are presence checks. They confirm a setting exists, not that it is right for your hardware.
  • The latency gate in this page takes a number you type. Only a real cyclictest run on the node measures jitter.
